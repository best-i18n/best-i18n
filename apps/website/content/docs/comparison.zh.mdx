best-i18n 最好的想法正是从这些被拿来对比的库继承来的，所以这一页与其说是比赛，
不如说是一张取舍地图。数字来自仓库里的孪生 playground——同一个应用、同样两个
页面、同样的消息，每个库各一份——用 `pnpm bench` 重新构建即可复现，而不是凭
记忆写下的。

## 一览

|                                      | best-i18n                                 | Lingui                        | next-intl              | Paraglide JS          |
| ------------------------------------ | ----------------------------------------- | ----------------------------- | ---------------------- | --------------------- |
| 消息是什么                           | 源文本                                    | 源文本                        | key                    | key（`m.greeting()`） |
| 运行时装载什么                       | 无——内联三元/字面量                       | catalog + 查找                | catalog + ICU 格式化器 | 每条消息一个函数      |
| catalog 格式                         | PO                                        | PO                            | JSON                   | inlang messages       |
| 复数                                 | gettext，公式按语言内联                   | ICU，运行时                   | ICU，运行时            | matching/variants     |
| `select`、日期、数字                 | 无——用 `Intl`                             | 有（ICU）                     | 有（ICU）              | 无内置格式化          |
| 消息内嵌标记                         | `<Trans>`，构建期重组为 JSX / Svelte 标记 | `<Trans>`，每次渲染遍历消息树 | `t.rich()` 运行时      | 仅字符串              |
| 按语言构建                           | `staticLocale`——纯字面量                  | 无                            | 无                     | 有，按语言出包        |
| 本地化路径（`/about` → `/de/ueber`） | 无                                        | 无                            | 有                     | 有                    |

Svelte 和 Solid 两族还各有一个完全没有编译步骤的运行时库：

|                   | svelte-i18n                                 | @solid-primitives/i18n        |
| ----------------- | ------------------------------------------- | ----------------------------- |
| 消息是什么        | key（`$_('greeting')`）                     | key（`t('greeting')`）        |
| 运行时装载什么    | ICU 格式化器（`intl-messageformat`）+ store | 扁平化字典 + `{{ }}` 模板填充 |
| catalog 格式      | JSON                                        | JSON 或任意对象               |
| 复数              | ICU，运行时                                 | 无内置                        |
| 消息内嵌标记      | 仅字符串                                    | 仅字符串                      |
| 按语言构建        | 无                                          | 无                            |
| locale 解析、路由 | 无——自己带                                  | 无——自己带                    |
| SSR 按请求绑定    | 无——一个全局 store                          | 无——你自己提供的 signal       |

其中两个是 best-i18n 的直系祖先：宏的形态和 `<0>...</0>` 标记约定来自 Lingui，
而 Paraglide 证明了编译期 i18n 加按语言 tree-shaking 根本上可行。与 Lingui 更深
的分野在于运行的东西：Lingui 在运行时查 catalog，`<Trans>` 每次渲染都遍历消息
树；这里每个语言的版本在浏览器看到之前就已经是普通 JSX 或 Svelte 标记。

## 实测体积

同族的应用用同一种方式测量——Next.js 上是 `/zh`、`/zh/about` 和 `/zh/long`
的 HTML 引用到的全部 `/_next/static/*.js`；TanStack Start 上是产出的客户端资
产；SvelteKit 上是 `.svelte-kit/output/client` 下的全部 JS；SolidStart 上是
`.output/public/_build` 下的全部 JS。`/zh/long` 是多文本场景：一篇刻意做长的文章，约 30 条服务端渲染的消息——
整段落、复数、上下文、标记俱全——在两个 Next 孪生里各有一份镜像。

| ---------------------------------- | ----------------- | -------- | ------------------ | ----------------------- |
| 完全没有 i18n                      | 173.4 kB          | 562.0 kB | 1.9 kB             | -                       |
| best-i18n                          | 174.3 kB          | 564.9 kB | 2.4 kB             | 5.0 kB                  |
| best-i18n，`I18N_STATIC_LOCALE=zh` | 174.2 kB          | 564.7 kB | 2.4 kB             | 5.0 kB                  |
| next-intl                          | 187.4 kB          | 607.4 kB | 4.9 kB             | 5.5 kB                  |

| 变体                               | 客户端 JS（gzip） | 原始    |
| ---------------------------------- | ----------------- | ------- |
| best-i18n                          | 16.7 kB           | 41.9 kB |
| best-i18n，`I18N_STATIC_LOCALE=zh` | 16.4 kB           | 41.3 kB |

Next 表的两列 HTML 就是全部故事。两边的首页渲染同样几条消息，`/zh` 却是 2.4 kB 对
4.9 kB：差额就是 catalog——next-intl 把它装进每个页面的载荷，无论页面渲不渲染
那些消息。best-i18n 的页面只携带自己渲染的文字——长文页那约 30 条消息只以
HTML 的形式存在于 `/zh/long`，别处都没有，客户端 JS 里也没有。长文页本身两边
接近（5.0 kB 对 5.5 kB）：真正渲染这些文字的页面为文字付费，无论是谁编译的。

## 这些差距各是什么做的

它们不是同一种差距，而这一点比数字本身更重要。

**next-intl 的约 13 kB 是消息运行时**——ICU 格式化器、catalog 和查找。它买到
的是复数、`select`、日期、数字和富文本。best-i18n 后来长出了自己的复数——
gettext 复数，编译成按语言内联的公式而不是 ICU 运行时——但 `select`、日期和
数字它仍然不做。next-intl 的 catalog 还默认随**每个**页面的 HTML 传输：`/zh`
一条 `/long` 页的消息都不渲染，却携带着全部约 30 条——就是上表里 4.9 kB 对
best-i18n 2.4 kB 的那个差距。

**Paraglide 的约 8 kB 是一个 URL 路由器**——`URLPattern` 匹配器、cookie 处理、
`preferredLanguage` 检测——不是消息查找。消息侧两个库都内联都 tree-shake，
所以差距是固定的，不随 catalog 增长。它买到的东西是实打实的：Paraglide 能翻译
路径本身，`/about` 变成 `/de/ueber`，这是 best-i18n 完全做不到的。这个路由器
有多重取决于外面的打包器：同一个 chunk 在 SvelteKit 的共享 chunk 里是 8.7 kB，
在 SolidStart 的构建里是 15.8 kB。

**svelte-i18n 的约 17 kB 是一个 ICU 运行时**——`intl-messageformat` 加 formatjs
解析器，每条消息都在浏览器里解析和格式化——再加每个语言一个字典 chunk。这和
next-intl 是同一笔交易，只是发生在客户端：复数、`select`、日期、数字，每个页面
都付一次钱。它也不带 locale 解析、路由和按请求绑定；playground 里这三样都是手
工补的，而服务端那一个全局 store 是按请求写入的——它自己的 SvelteKit 指南就是
这么做的——不同语言的并发请求会在这里竞争。

**@solid-primitives/i18n 的约 1.5 kB 几乎算不上运行时**——一个扁平化的字典加
`{{ name }}` 模板填充——所以它是所有测过的方案里离 best-i18n 最近的。两个懒加载
的字典 chunk 都被计入了，虽然访客只下载一个。和 svelte-i18n 一样，它到翻译为止：
playground 里的 locale signal、URL 前缀、中间件和 context provider 全是应用自己的
代码。它没有复数。

## Svelte 与 Solid

这两个生态里的运行时库对自己的范围很坦诚：它们负责格式化文字，周边一切留给你。
best-i18n 带给 Svelte 和 Solid 的，除了编译步骤，正是它们留下的那部分——解析链、
URL 辅助函数、SSR 用的 `withRequestLocale`——以及四个替代方案都没有的一件事：消息
内嵌标记。它们每一个都得把 `Read the <a>README</a> to learn more.` 手工拆成三个
字符串，从而把每种语言的词序都钉死；`<Trans>` 保持它是一条消息，构建期按语言重组
为 Svelte 标记或 Solid JSX。

另一条轴是响应式。Paraglide 的 `setLocale()` 会整页导航，所以什么都不需要响应式。
svelte-i18n 是 store——`$_` 和 `$locale`——`@solid-primitives/i18n` 是你传进去的
signal。best-i18n 编译出的 locale 读取接入了各框架自己的响应式系统——Svelte 里是
`createSubscriber`，Solid 里是 signal——所以模板里的 `` t`...` `` 会原地更新，而在
URL 也该变的时候 `switchLocale` 仍然走整页导航。

## best-i18n 更贵的地方

消息在每个调用处内联。同一个模块内的重复会坍缩：重复消息的各调用点共享一个提升
到模块顶部的函数——Paraglide 的形态——所以它的翻译在每个模块里只输出一份。
跨模块时每个模块各带一份拷贝，因为 transform 有意保持逐文件处理；gzip 会把这种
重复压平（实测一条消息用 100 次为 **+0.5 kB gzip**，内联或提升皆然），走网络是
平手，剩下的是解析时间。

**为什么现在不做跨模块去重。** 它是可行的——一个虚拟模块，每条消息一个函数，
由所有调用处 import，大致就是 Paraglide 生成的 `messages/` 目录的形态。这里有
三点理由不这么做。

transform 每次只拿到一个文件。Vite 和 Rolldown 的 `transform` 钩子、Next.js 的
loader，交给插件的都是单个模块，看不到模块图。所以共享模块要么需要一趟在构建
之前写文件的 codegen，要么需要一个所有用到消息的文件都得 import 的虚拟模块。
两者都会放弃当前设计里最省心的那条性质：编译产物是自包含的，打包器开始之前不
需要先跑任何东西。

而且它也不会在真正要紧的那条边界上去重。App Router 里服务端和客户端是两张独立
的模块图，两边都渲染的消息无论如何都会各留一份。

再说收益本来也不大。模块内的重复已经坍缩成一个提升出来的函数；跨模块的部分
gzip 会把它压平，剩下的只是重复字符串字面量的解析时间——为此往应用里每个模块
都插一条构建图上的边，并不明显划算。

那个提升出来的函数本身就是这样一个模块该导出的形态，所以真出现能测出代价的场
景，它是一处收敛的改动，而不是重新设计。

消息侧的规模也测过，加 300 条消息：从 Server Component 渲染时 best-i18n 的客户
端 JS 成本为零，从 Client Component 渲染时两种语言合计每条约 6 字节 gzip。

诚实清单的其余部分——没有 ICU `select`、Next.js 私有 API、`AsyncLocalStorage`
从哪来——在[限制](/zh/docs/limitations)。孪生 playground（
[`playground/nextjs-intl`](https://github.com/best-i18n/best-i18n/tree/main/playground/nextjs-intl)、
[`playground/tanstack-start-paraglide`](https://github.com/best-i18n/best-i18n/tree/main/playground/tanstack-start-paraglide)、
[`playground/sveltekit-paraglide`](https://github.com/best-i18n/best-i18n/tree/main/playground/sveltekit-paraglide)、
[`playground/sveltekit-svelte-i18n`](https://github.com/best-i18n/best-i18n/tree/main/playground/sveltekit-svelte-i18n)、
[`playground/solid-start-paraglide`](https://github.com/best-i18n/best-i18n/tree/main/playground/solid-start-paraglide)、
[`playground/solid-start-primitives`](https://github.com/best-i18n/best-i18n/tree/main/playground/solid-start-primitives)）
里有完整的数字和全部前提条件。
